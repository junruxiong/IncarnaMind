# Answers are produced by a tool-calling loop, not a fixed pipeline

**Amended 2026-10-09 by ADR-0013:** the product stays documents-first, but the core no longer rules out general-agent work: Tools come from Tool providers and declare their Effects, and an Answer is one kind of Run. The loop library sits behind a `RunEngine` interface. The choice below ("AI SDK 7, not pi") was measured again in the bake-off on `prototype/engine-bakeoff` (2026-10-09; scorecard committed before any run, speed weighted 15%): AI SDK 7 86.3, pi-agent-core + pi-ai 71.1, pi-coding-agent 68.4 out of 100. The three gave the same replies and passed the same safety and robustness checks; pi cost a 216-line model bridge, a build change for its ESM-only packages, +77 to +98 packages, about twice the code and 130–620 ms more at app start. AI SDK 7 stays, behind the `RunEngine` interface, so the choice remains reversible. Other frameworks were surveyed (`docs/research/agent-frameworks.md`); only fully open-source ones are considered, so Mastra (source-available enterprise code in its package, telemetry on by default) and the OpenAI Agents SDK (traces sent to OpenAI by default) were not added.

An Answer is generated by letting the chat model call tools until it is done. The first tool searches the User's Documents, and the sliding-window grouping of Passages lives inside that tool. MCP servers and skills add more tools and are part of version 1, built right after the notebook core.

The old backend used a fixed pipeline: split the question into sub-questions, pick relevant files, search, then answer. We replaced it for two reasons. MCP and skills need a tool loop anyway. And the loop removes two extra model calls, because the model itself decides how many searches to run and what to search for.

## Considered options

**Becoming a general desktop agent like Tencent's WorkBuddy**: rejected. IncarnaMind stays a documents-first notebook. Tools extend what a Question can draw on and do, rather than turning the app into a general computer assistant.

## Consequences

Models that can't call tools, and small local models that can (below), instead get a single search using the Question's text, with the results added to the Question context. When there are Blocks above the Question, that model first makes one short call to rewrite the Question into a self-contained search query from them, like the old CLI's condense step but producing one query, so a follow-up such as "what about its limitations?" searches for what "its" means; with nothing above the Question, or if the rewrite fails, the Question's own text is searched.

**Searching again in the Documents' language (#67, 2026-10-10).** The search Tool tells a model in the loop to search again with the query translated into the Documents' language when the Question is in another (ADR-0009: search finds Passages best in their own language; the evaluation's cross-lingual Questions are found 1 or 2 times in 10 without that second search, 7 or 8 with a hand-made one). A model without Tools can't, so the engine does it for it (`searchLanguage` in `src/core/answers/engine.ts`): when some of the Documents to search are in a language the Question isn't in (by `detectLanguage`; a Question too short to tell is known not to be in Chinese, Japanese or Korean when it has none of their scripts), the model makes one more short call to translate the query into the most common such language, and that is searched too. The Passages of both searches are given once each, ranked alternately, so a window too small for all keeps the best of each. The cost: in a library of Documents in two languages, every Answer of such a model makes the short call and a second search. If the translation fails or comes back empty, only the first search counts.

**Small local models cite with structured output (#67, 2026-10-09).** A model in Ollama with fewer than 7 billion parameters (`/api/show`'s `general.parameter_count`, else its `parameter_size`) answers as a model without Tools does, even when it can call them: one search, then the Answer and its Citation records as one JSON object, the engine placing the markers it leaves out (`citingMode` in `src/core/providers/ollamaModels.ts`). The Answer's phases show it as before: searching, the model loading, writing; its `citationSupport` is "structured-output".
- **Why:** in the Tool loop, small models search but don't call `cite`. qwen3.5:4b gave no Citation on 10 Documents Questions in the engine bake-off (`prototype/engine-bakeoff`), Llama 3.2 3B none on 8 (`docs/research/ollama-integration.md`).
- **What structured output gave instead**, in a probe of 20 evaluation Questions (10 English, 10 Chinese) with the app's own prompt, qwen3.5:4b at `num_ctx` 8,192, five Passages a Question with the expected one among them: records with all 20 Answers; on the cited pages, 17 of 19 English quotes and 11 of 15 Chinese ones word for word. Three of the four Chinese misses wrote the fixtures' traditional characters in simplified ones, which the Citation check didn't match then (it does since ADR-0009's amendment of 2026-10-10). Temperature 0, no presence penalty, an instruction to copy characters exactly, a second request to fix the quotes, a cap on a quote's length and thinking did no better; thinking took 80 to 100 s an Answer and often ran out of room before its JSON.
- **Its records are placed, as `cite`'s feedback lets a model in the Tool loop place them (2026-10-10).** In the loop, `cite` tells the model which records it can't check ("the quote isn't word for word on p. 7 in P2") and the model may fix them with another call. Structured output's one request gets no such word, so the engine reads its records as meant (`CiteOptions` in `src/core/answers/engine.ts`): a marker written as in the Answer ("[^1]") is 1; a Passage named by its number alone ("1"), or its id with more ("P1 (p. 9)"), is "P1"; a record naming no Passage it was given, such as its Document's name (the likely reason six of qwen3.5:4b's records were dropped in a short check on 2026-10-10; the Answer's end now reports each record the core couldn't take, as given), cites the first Passage it was given whose pages hold its quote word for word; and a quote that isn't on the pages its record names, but is word for word on a page of the Passage it names, or on two consecutive ones, is cited there. A record is never moved outside the Passage it names, and the Citation check still reads the quote on the pages it ends up citing, so a quote that is nowhere stays "not found". Offline cases: `tests/eval/smallModelCitations.test.ts`.
- **A second chance at quotes not found (2026-10-10).** What: when the check doesn't find some of a local model's quotes in structured output, once placed, the engine asks the model once more, in one request for all of them (at most 6): each record's marker, the Answer's sentence it is on, its quote, and its Passage's text (the 400 tokens nearest the quote when the Passage is longer), for an exact quote copied from that text, or none; a new quote replaces a record's only when the check finds it on the pages it then cites, so a Citation can't get worse (`src/core/answers/quoteRetry.ts`). Why: qwen3.5:4b's remaining misses on the gating set (English 96.1%, Chinese 89.4% of quotes found) are quotes reworded, or stitched from two sentences, which `cite`'s feedback lets a model in the Tool loop fix and one structured request can't; the probe above found a second request no better, so the evaluation now measures this one. Cost: nothing for an Answer whose quotes are all found, never for cloud models or the Tool loop; otherwise one request with an output cap of 100 tokens a record, shown in the Answer's phases ("Checking quotes…") and reported at its end (`quoteRetry`), from which the evaluation counts the Answers that made it, the records it recovered and the time it added (`eval/README.md`).
- **The cost:** such a model searches once, for the Question (twice when some Documents are in another language, above), and isn't offered Skills' or Connectors' Tools (a Skill the User picks for the Question still applies). In the bake-off qwen3.5:4b handled those Tools unreliably too: it said it had closed an issue after the User denied the call.
- **Unchanged:** models from 7 billion parameters up, those whose size Ollama doesn't give, and cloud models keep the Tool loop: nothing was measured that would move them. `npm run eval` measures a local model's citing modes on the same window with `INCARNAMIND_EVAL_CHAT_NUM_CTX` and `INCARNAMIND_EVAL_CHAT_CITING` (`eval/README.md`).

## The loop's library: AI SDK 7, not pi

Confirmed by the User on 2026-10-07, after the spike on `prototype/pi-agent` (its README has the evidence). The loop is built on AI SDK 7's `ToolLoopAgent`, with the official MCP SDK for Connectors and our own small `SKILL.md` loader. We don't adopt `pi-coding-agent`, nor `pi-agent-core` with `pi-ai`. The reasons:
- **pi-coding-agent is a coding-agent product, not a library.** It reads and writes `~/.pi`, discovers its own Skills and `AGENTS.md` files, and can't be fully isolated. It keeps Connector tokens in a plain JSON file, which breaks the keychain requirement.
- **It doesn't load in our CommonJS main process.** It is ESM-only.
- **It is heavy.** It adds 98 packages and 153 MB, plus a second set of provider SDKs.
- **It saves no code.** The same tested behaviour took about 380 lines on pi and 231 on AI SDK 7.
