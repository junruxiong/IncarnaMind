# Each Mind is stored as one CRDT document (Yjs)

Each Mind's content is a single Yjs document that the editor edits directly. It is not stored as one database row per Block with a numeric order. We chose this because the hosted version must sync Minds across devices (ADR-0002). Yjs merges edits made offline on different devices without conflicts, so adding sync later means relaying updates, not migrating data. It also removes the job of translating editor changes into insert/reorder/delete calls, which the old frontend never got working. The cost is that finding Blocks in a Mind, such as the ones above a Question, means reading the document instead of running a query.

## Consequences

Version 1 has no sync, but it follows these rules so sync can be added without migrating data:

- A Document is known by where its file belongs, its Linked folder and its path inside it, never by a path on one device, and a hash of its content identifies each version (ADR-0020). This replaced identifying a Document by its content hash, which ADR-0010 had already narrowed.
- Every ID is a random UUID generated on the device, never an auto-increment number, so two devices can't produce the same ID.
- Deleting something marks it deleted rather than removing the row, so a later sync can tell other devices about the deletion.
- Secrets (API keys, OAuth tokens) are kept only on the device and never go in data that will be synced.
- Settings are split into per-device (window size, file paths) and per-User (default model, interface language). Only per-User settings will sync.

## Amendment: kinds, a content schema version, one reference shape, and Citations

Chats now, and sheets, decks and boards after the alpha, are stored the way Minds are, so the storage leaves room for them and stays safe once Minds sync between computers running different versions.

- **Kind.** Each Mind has a `kind` on its row, `mind` by default (`chat` for a chat). A Mind of a kind this version doesn't know is listed, but it opens as "Update IncarnaMind to open this", never in the editor, and the core refuses to write to it.
- **Content schema version.** A Mind's Yjs document records, in its settings map, the content schema version it was last written with (`CONTENT_SCHEMA_VERSION` is the newest this version understands: 2 since tables, #92, 3 since footnotes, #284, 4 since Proposals, #93, 5 since a Proposal records the text it changes, #94, 7 since charts, #436, 8 since Document chips and checklists, #115, 11 since AI text, #95, and 15 since what a Word import keeps as it is, #104). A Mind with none reads as version 1. The core records its version on every write and never lowers one. A Mind written by a newer version opens read-only with a notice to update: the editor's Yjs binding deletes node types and marks, and strips attributes, that its schema doesn't know, which would silently destroy another computer's content once sync exists. For such a Mind the core neither compacts nor accepts any update, so its Yjs state stays byte for byte as it was. Raise the version whenever a change would make an older version lose or misread content (a new node type, mark or attribute). A raise that only adds node types needs no rewrite of older Minds: their content is valid as it is, and they record the new version on their next write. A chart (version 7) is such a node: it keeps the Citation of each value it draws in its own attributes, and the start-up walk that keeps the versions Citations quote reads them there too. The same holds for a raise that only adds marks or attributes: version 4 adds the `proposalInsert` and `proposalDelete` marks and a `proposal` attribute on Blocks and inline nodes, which older content simply doesn't have, and version 5 adds a `target` to them, without which a Proposal is never out of date. Version 8 adds node types: the `documentChip` inline node the User writes with "@", which names a Document by its id (and keeps its name as it was, for when the Document is gone), and the `taskList` and `taskItem` nodes of a checklist, whose items keep `checked`.
- **Proposals are content, kept with the Mind.** A change the AI made that waits for the User (a Proposal) is stored in the Mind's Yjs document itself, so it survives sync and reload and any device can resolve it: words it removes stay, under `proposalDelete`, and words it adds are there, under `proposalInsert`; a whole Block or an inline node it adds or removes carries the `proposal` attribute (the editor's Yjs binding keeps no marks on nodes). Each names its Proposal and the request that made it; a `proposalRequests` map beside the Blocks says which model made each request, and is kept once written. Accepting or rejecting is one Yjs change, defined once (`src/shared/proposals.ts`) for the core and the editor. What reads a Mind's text (Question context, exports) reads it as accepted: without what Proposals add, with what they would remove.
- **One reference shape.** A reference from one artifact to another is `{ artifactId, anchor }`. The anchor is a Block's stable ID for now (`{ kind: "block", blockId }`), never a position, so the reference survives edits and sync. It is used for a Block's origin and for the link back from a Note to the chat it came from.
- **Citations stay editor-independent.** A Citation's target is always a Document location (a Document and where in it), independent of the editor and of the artifact that holds the Citation. Citations are checked against Documents, never against Blocks or any artifact's structure, so a Citation means the same in a Mind, a chat or a later kind of artifact.

## Amendment: conversations are not Minds (2026-10-11, ADR-0017)

The assistant's conversations are kept by the core in SQLite, not as Minds (ADR-0017), so two things above change. The `chat` kind is retired: `mind` is the only kind this version opens, and `kind` stays for sheets, decks and boards. And a reference names its artifact's kind, `{ artifactKind, artifactId, anchor }`: a Mind's anchor is a Block, a conversation's is a message (`{ kind: "message", messageId }`). A reference stored without `artifactKind` is a Mind's. Citations stay as above: a Citation in a conversation is checked against its Document like any other.

## Amendment: where third-party text came from (2026-10-11, #78)

A Mind's Yjs document keeps, beside its Blocks, a `textOrigins` map: for each Block, top-level or nested, that holds third-party text (ADR-0013, amended), where it came from ("imported", "web-page" or "checked-document"), by Block id. It is a map rather than a Block attribute: an attribute would have to be declared on every node type a Block can be, nested ones too, and an older version's editor would strip it unless the content schema version rose, which would make every Mind written since open read-only there. An older version keeps the map as it is, so the content schema version stays 4. A Block deleted since leaves its entry unused. A copy pasted elsewhere gets a new id and counts as the User's, as text pasted from another app does.

## Amendment: when each line of a Meeting's notes was written (2026-10-12, #139)

A Mind's Yjs document keeps a `blockTimes` map beside its Blocks: for each line the User writes while the Meeting records, the Meeting's time in ms, by Block id. It is a map for the same reason as `textOrigins`: an attribute would make an older version's editor strip it, or need the content schema version to rise, so the version stays as it is. A line takes its time when it first has text, a Mark when it is made, and nothing is taken while the Meeting is paused or stopped. A Block deleted since leaves its entry unused; a copy pasted elsewhere has no time.

## Amendment: AI text is a mark on its words (2026-10-12, #95)

The words the AI wrote that the User hasn't made their own carry a `generated` mark, kept in the Mind's Yjs document as a formatting attribute of their text, so it survives sync and reload and any device draws it the same. It is a mark, not a map beside the Blocks like `textOrigins`: it belongs to words, not Blocks, and has to split and follow them as the User types inside AI text, which only text formatting does. What the User types never takes it, and "Mark as mine" takes it off. Older Answers have no marks; an Answer written since carries `generatedMarks: true`, and one without is AI text as a whole, as it always was. An older version's editor would strip the mark and the attribute, so the content schema version is 11; nothing older is rewritten. Readers and exports treat the mark as no mark.

## Amendment: a Mind imported from a Word file (2026-10-12, #104)

A Mind can be imported from a .docx (ADR-0011, amended), and export writes the User's edits back into the original package (#105), so the Mind keeps what that needs.

- **Content schema version 15** adds three node types: `wordAtom`, inline, and `wordBlock`, a Block, for what the editor can't represent and keeps as it is (a field, a text box, a bookmark, a header…), each naming where its XML is in the package; and `image`, an inline picture. Older content is version 15 content as it is. A version before 15 opens a Mind with any of them read-only.
- **Beside the Blocks,** two maps, as `textOrigins` is, so an older version keeps them as they are: `word` (the file: its name, the package's SHA-256, size and main part; whose document it is; what the import made editable and kept as is; how far the import has got) and `wordSources` (for each node mapped from a paragraph or a table, by node id: its `w14:paraId` or its place in the part, and its fingerprint as imported, which tells export whether it was edited).
- **The package** isn't in the Yjs document: it is kept in the data folder by its SHA-256 (ADR-0011), with a row per Mind (migration 69), and would sync as a file of its own.
